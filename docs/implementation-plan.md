# 实施计划与验收标准

## 已明确的需求

用户要求将 DeepSeek harness 封装到 Docker，一个智能体一个容器，每个版本具有唯一标识，并提供一键安装部署。实施和学习过程需要逐步记录。先在 Windows 电脑上封装和测试，确认无误后再由用户部署至 Linux 服务器。

上游已确认为 https://github.com/deepseek-ai/deepseek-harness 。未来业务为 MRI 控制台操作，使用远程桌面，计划自行部署模型。用户明确当前先完成封装、镜像和部署，不以模型、GPU 或远程桌面协议选择为前置条件。

## 需要确认的信息

当前封装工作无待答复的前置问题。模型型号、服务器 GPU、远程桌面协议、MRI 任务标准、专家与 manager 分工留到后续集成阶段。当前镜像目标为 linux/amd64；若未来服务器为 ARM64，需要单独构建与验证。

## 拟采用的版本方案

实现采用唯一发布 ID、精确依赖锁、镜像 ID 校验和构建输入归档；各次测试状态见学习记录与测试报告。

- Git 保存源码、部署脚本、依赖锁定文件、变更记录和学习记录。
- 每次发布生成唯一发布 ID，并绑定语义版本、可用的 Git commit、构建输入逐文件 SHA256 和构建元数据。Git 未提交的工作树以输入快照为准。
- 镜像使用唯一发布标签；发布清单记录镜像内容摘要。已发布版本不覆盖，同一标签不用于另一次发布。
- 发布版本与智能体实例分开管理：多个实例可以运行相同版本，但实例 ID、数据目录和日志必须独立。
- 回滚通过指定历史版本完成；如涉及持久化数据结构变更，需同时提供兼容性说明或迁移／恢复方案。

## 实施顺序

| 阶段 | 工作内容 | 完成标准 |
| --- | --- | --- |
| 1 环境检查 | 确认代码位置、Docker、Compose 与引擎架构 | 已检查本机工具并核验上游项目 |
| 2 基础封装 | 接入真实 harness，编写 Dockerfile 和实例配置 | 容器能够启动并打开认证后的 Web UI |
| 3 版本管理 | 实现唯一发布 ID、版本清单与可追溯构建 | 能从运行实例定位代码和镜像版本 |
| 4 一键部署 | Windows PowerShell 和 Linux shell 入口 | 前置检查、安装／构建、启动与健康检查形成完整流程 |
| 5 本机验收 | 功能、重启、隔离、持久化和回滚测试 | 实测结果与错误处理均有记录 |
| 6 Linux 交付 | 核对架构与配置，编写迁移说明 | Windows 验收通过后，提供 Linux 部署材料 |

## Windows 验收清单

以下项目均未执行，不代表已经通过。

- 一条命令完成应用部署；缺少 Docker、配置或 API 密钥时给出可执行的提示。
- 固定版本的官方 harness 可以启动并访问 Web UI。真实模型调用与 MRI 任务属于后续业务验收。
- 两个实例分别使用自己的配置和数据，无非预期共享。
- 容器重建或重启后，按约定保留必要数据。
- 能检查健康状态、查询日志并正常停止服务。
- 每次发布的标识唯一，运行版本可以追溯。
- 在数据兼容的前提下，升级和回滚均能正常执行。
- 日志和构建上下文不包含真实密钥。
- 镜像导出、校验与导入可以在同一 Docker 环境往返完成；实际 Linux 服务器由用户后续验证。

## 记录方式

每个阶段记录目的、知识点、实际命令或变更、观察结果、问题原因、解决方式和下一步。失败操作也记录。只有实际执行并检查过的项目才能标记为通过；尚未执行的方案明确标记为计划。
